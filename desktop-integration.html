Workshop / Desktop integration
Implementation note · 15 October 2026

Mechanics today. Native mediation tomorrow.

A window on the host.
A process in the guest.

Running a desktop app in Workshop requires several independent connections. This document separates what each capability needs, who provides it, and where the current proof of concept leaves mediation to improve.

“Guest” means the Workshop container. Firefox adds a second confinement boundary through Snap.

The central design point

Display access, desktop service calls, device access, media streams, and launching host applications are separate grants. D-Bus is necessary for D-Bus services; it is not a universal multimedia bridge.

00

Separate the capabilities

The app runs as the unprivileged Workshop user. Its window appears through Workshop’s existing desktop connection. Everything else needs its own transport and policy.

Screen sharing needs a separate screencast/portal path. GPU access supports rendering, but does not itself prove hardware decoding or DRM support.

D-Bus proxying & notifications

Yes: traditional desktop notifications use org.freedesktop.Notifications on the session bus. Portal-aware apps can instead use the Notification portal. Forwarding the chosen service enables its calls; it does not automatically solve application identity, file paths, or activation.

Guest applicationExplicit host session bus address
→
Host xdg-dbus-proxyMounted socket + allowlist
→
Host desktop servicesNotifications and portals
Host responsibility

Authenticate and filter

bin/workshop-desktop host dbus starts a session proxy as the logged-in desktop user. It connects to the real host session bus and publishes a private socket. --filter exposes selected bus names instead of the entire host bus.

There is no host system-bus proxy. The guest keeps its local system bus for snapd.

Guest responsibility

Select the bus at the right time

Session proxy: /mnt/workshop-host/session/bus, exposed through a read-only directory bind mount at /run/user/1000/snap.firefox/hostbus so Firefox’s Snap policy can access it.

Firefox starts through the local session bus for its systemd scope, then switches to the host proxy inside the Snap command chain.

Actual proxy rules in internal/hostcmd/dbus.go
BusAllowed namePurpose / scope
Sessionorg.freedesktop.NotificationsDirect notification calls. Validate display, close, and action signals.
Sessionorg.freedesktop.portal.Desktop
org.freedesktop.portal.Documents		Portal services. A service-name grant is broader than granting only notifications or URI opening.
# Unconfined guest app opting into the generic host session proxy:
export DBUS_SESSION_BUS_ADDRESS=unix:path=/mnt/workshop-host/session/bus

Keep local buses local. Guest snapd needs the guest system bus; the guest user manager needs its own session bus. Firefox retains the local system bus. Unused host login1/UPower proxying, the host keyring grant, and Firefox bus-name ownership have been removed.

Remaining challenge: the proxy filters bus access but is not a semantic desktop broker. Notification icons may refer to guest-only files; action clicks need routing back to the app. Portal calls need trustworthy app identity and, for file selection, usable document mounts.

Code: proxy allowlist · bus-switching launcher · runtime bind mount. Protocol: Desktop Notifications; proxy: xdg-dbus-proxy.

02

Camera: device access today

This proof of concept uses Workshop’s native camera interface. It exposes capture devices directly; the camera stream does not travel through the D-Bus proxy or the audio bridge.

Host cameravideo4linux + media devices
→
Workshop camera interfaceDevice exposure and hotplug
→
Guest capture clientFirefox Snap → website permission
Host responsibility

Connect the hardware boundary

The helper connects the Firefox SDK’s camera plug. Workshop exposes existing /dev/video* and /dev/media* devices and tracks additions and removals while connected.

The current native interface covers all matching devices, rather than a per-request camera chooser.

Guest responsibility

Pass both confinement layers

The SDK declares interface: camera. Its setup hook connects firefox:camera inside Snap. The Workshop user must also be able to access the device nodes.

Firefox still asks websites for camera permission. That prompt governs the website; it is not a host-wide grant for every guest process.

# Host (also performed by bin/workshop-desktop host connect):
workshop connect firefox/firefox-desktop:camera

# Guest device nodes; actual frames still need a browser capture test:
workshop exec firefox -- sh -c 'ls /dev/video* /dev/media*'

Remaining challenge: discovering a device is not proof of frames. Validate actual capture, format negotiation, device contention, hotplug, and disconnect behavior. A future portal camera path would be a different implementation, needing portal authorization and a suitable PipeWire stream; allowing the portal bus name alone does not establish it.

Code: camera declaration · Snap connections. Native behavior: Workshop camera interface.

03

Microphone & speaker audio

Input and output share the same bridge. Apps speak PulseAudio in the guest; the guest compatibility server connects to the host PipeWire graph. The host session manager selects and links the available devices.

Guest audio appPulse socket → guest pipewire-pulse
↔
Mounted security-context socketpw-container on the host
↔
Host PipeWire graphMicrophone, speakers, session manager
Host responsibility

Publish a scoped entry point

A running PipeWire server with SecurityContext support and a session manager is required. pw-container creates the socket; the helper moves it into the mounted directory and keeps the process alive.

Publication uses rename, so the source socket and the destination under /tmp/workshop-desktop-<HOST-UID>-<PROJECT-ID>/pipewire/ must be on the same filesystem; cross-filesystem publication fails.

The helper supplies app ID org.mozilla.firefox and an instance ID. These labels are not independently verified per guest application.

Guest responsibility

Provide PulseAudio compatibility

workshop-pipewire-pulse.service runs pipewire-pulse against the mounted remote. Distribution PipeWire, Pulse socket activation, and WirePlumber units are masked to avoid competing services.

The host-audio SDK owns this service and its on-demand command wrapper. No separate guest graph or session manager is started. The Firefox SDK owns its Snap audio-playback and audio-record permissions.

# Guest service environment:
PIPEWIRE_REMOTE=/mnt/workshop-host/pipewire/pipewire-0
XDG_RUNTIME_DIR=/run/user/1000
DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus

# Client environment selected by the reusable audio wrapper:
PULSE_SERVER=unix:/run/user/1000/pulse/native

Use the native socket. PipeWire’s native protocol passes file descriptors. The implementation mounts the directory containing the security-context socket; an ordinary byte-stream relay cannot preserve those protocol semantics. It does not mount the host’s ordinary pipewire-0 or PulseAudio socket.

Remaining challenge: a security context carries identity properties, but effective permissions depend on host session-manager policy. This setup does not promise playback-only access or separate microphone consent. A compatibility server can aggregate multiple guest apps behind one connection, limiting attribution. Native mediation should distinguish playback, microphone capture, and speaker-monitor capture, and enforce revocation for each.

Choose a real microphone source: a source ending in .monitor captures speaker output. The browser’s website prompt is another layer; it cannot substitute for host device policy.

Code: pw-container lifecycle · guest audio service · audio wrapper and client environment. Mechanics: pw-container · native protocol. Policy: WirePlumber client access.

04

Open URLs & files on the host

The host should choose its registered application. The guest should express an opening request, with an explicit way to translate shared files across filesystem namespaces.

Guest open commandxdg-open wrapper → guest open
Normalizes URI or shared file
→
Private Unix socketOne JSON request + response
→
Host openerChecks peer → host xdg-open
Host responsibility

Validate and dispatch

bin/workshop-desktop host open checks peer UID against the host user, bounds the request to 16 KiB, rejects control characters, and translates local file: URIs under /project into the checkout.

It resolves the host path and rejects escapes through symlinks. It executes ["xdg-open", target] without a shell. Non-file URI schemes go to host handlers without a scheme allowlist.

Guest responsibility

Install a compatibility entry point

The host-open SDK uses dpkg-divert to retain the packaged utility as /usr/bin/xdg-open.distrib and installs the shared static Go binary at /usr/local/bin/workshop-desktop with an /usr/bin/xdg-open wrapper that runs workshop-desktop guest open "$@", covering PATH and absolute-path callers.

Relative files are resolved in the guest and must remain under /project. Requests go to /mnt/workshop-host/open/socket. The guest bounds requests and responses to 16 KiB and applies a five-second overall timeout; the host gives each connection a three-second I/O deadline.

# Requests from the guest, dispatched by the host:
workshop exec firefox -- xdg-open https://example.com
workshop exec firefox -- xdg-open mailto:someone@example.com
workshop exec firefox -- xdg-open /project/README.md

# The same guest client, invoked explicitly:
workshop exec firefox -- /usr/local/bin/workshop-desktop guest open https://example.com

“And equivalent” is still a gap. Toolkit calls, gio open, direct D-Bus calls, portal OpenURI/OpenFile, and utilities bundled inside Snap may bypass this shim. Firefox’s Snap uses its own utilities and portals. The existing portal allowlist makes that route possible to investigate; it does not prove equivalent host-opening behavior.

Files need a contract. Guest-only files currently have to be copied to /project. The portal API separates URI opening from local file opening: OpenURI excludes file: URIs; OpenFile accepts a file descriptor. A native broker should define shared-path translation or controlled file export, plus parent-window/activation handling and request results.

Current result semantics: ok: true means the launcher did not fail immediately (within 0.2 seconds). It does not prove that a window appeared or that the chosen application successfully opened the target. Peer UID protects the socket boundary, but does not identify an individual guest app.

Code: host request validation · guest Go client · opener tests. Equivalent API: OpenURI / OpenFile portal specification.

One binary, explicit host & guest commands

One Go standard-library tool, workshop-desktop, provides every host helper and the guest opener. Host handlers can run together with host serve or individually, with independent capability locks. Runtime diagnostics use Go’s slog text handler on stderr.

The single command entrypoint dispatches to internal/hostcmd or internal/guestcmd. Guest commands dispatch before host initialization: they do not load .workshop.lock, create host project directories, or apply the host desktop-user check. Host commands default to the current directory and require its .workshop.lock from a Workshop launch. Each accepts --project PATH; host connect also accepts --workshop NAME, but expects the same SDK and plug names as the Firefox definition. This flag does not change SDK composition.

internal/host owns shared host lifecycle, project paths, flags, signals, and capability locks. internal/pipewire publishes the native socket. internal/opener shares the client/server protocol and handles credentials, URI/path validation, and launching. Consolidation changes command dispatch and packaging; the mounted transports and capability boundaries remain separate.

The dev build stages the same binary into the host-open SDK. Its install hook checks that it exists before changing the guest, installs it under /usr/local/bin, and diverts the packaged xdg-open before installing a small shell wrapper. The wrapper executes /usr/local/bin/workshop-desktop guest open "$@" and preserves arguments and exit status. The runtime SDK needs neither Python nor a Go toolchain; host and guest must match the build architecture.

workshop launch dev
workshop run dev -- build
workshop run dev -- test
workshop run dev -- fmt

The dev workshop uses Go 1.27 and emits one static Linux binary at bin/workshop-desktop, also staged at .workshop/host-open/bin/workshop-desktop. Run its host commands in the host graphical session. The staged copy supplies guest open inside Firefox’s workshop. The firefox workshop composes the three feature SDKs with the Firefox app SDK. Its action runs workshop-host-audio workshop-firefox; audio setup is outside the app launcher. Multiple definitions live under .workshop/; there is no root definition or Makefile.

Host root: /tmp/workshop-desktop-<HOST-UID>-<PROJECT-ID>/
Host subdirectoryGuest mountEndpoint
session/mnt/workshop-host/sessionbus; also bind-mounted under Snap runtime
pipewire/mnt/workshop-host/pipewirepipewire-0; native security-context socket

Directories are private (0700); mounts map ownership to guest UID/GID 1000. Sockets sit outside guest /run so boot-time mounts do not hide them. A late systemd mount exposes the session proxy under snap.firefox after the user runtime directory exists. Read-only directory mounts still permit connecting to sockets; they do not limit the service’s authority.

Handler lifecycle: an individual helper closes only its own capability. With host serve, selected handlers run concurrently in one process; failure of any selected handler stops the group; Ctrl-C/SIGTERM waits for all selected handlers to clean up. Only selected capabilities are locked. D-Bus and PipeWire children receive SIGTERM with a bounded wait before forced termination. Locks prevent duplicate helpers from replacing active sockets. Reconnect after host reboot if /tmp was cleared; restart affected guest clients if needed. The previous combined workshop/profile is not automatically migrated or deleted.

07

A brief for native Workshop interfaces

The following are design proposals, not interfaces implemented by this repository or claims about Workshop’s current API.

Capability contractWhat native mediation should own
Desktop service accessDeclarative session/system service grants; separate notifications, portals, and secrets. Preserve local buses and expose a managed endpoint to compatible app launchers.
NotificationsWorkshop/app attribution, safe icon transfer, return action signals, close/update semantics, and permission revocation. Prefer a specific grant over unrestricted portal-service access.
CameraKeep direct device access as an explicit mode. Explore selected-device or portal-mediated capture with host consent, hotplug, active-use visibility, and tested disconnect semantics.
Audio playback / captureSeparate playback, microphone, and monitor capture policy. Own security-context creation and guest compatibility service; define whether grants apply to a whole workshop or individual apps.
Host openingA common broker for utility, toolkit, and portal callers. Define URI policy, shared-file translation/export, activation, failures, and asynchronous results.

One lifecycle. Several explicit grants.

Workshop could manage per-session host endpoints, mount ownership, guest environment, confinement adapters, health checks, reconnect, and cleanup. Capability policy should remain separate, so connecting a display does not silently enable recording, host secrets, or application launching.

First decide the unit of trust: the whole workshop, an SDK, or a verified application. The current shared sockets and audio server mostly act at workshop scope; an app-ID string and Unix UID alone cannot establish per-app isolation.

Refactor now in place: one binary exposes explicit host and guest subcommands. Host capabilities retain separate locks and cleanup. They can run as concurrent handlers in one host serve process or as separate helper commands; D-Bus and PipeWire still use child processes. The next native-interface step is to own mount/session lifecycle and enforce grants in Workshop, then replace app-specific runtime paths and bus-switch timing with a supported confinement adapter. Define readiness and revocation per capability.

08

What would constitute proof?

Current evidence is implementation, not a live desktop result. Live Workshop and Firefox integration remain unverified; automated helper and wrapper checks provide narrower evidence. This document reviews the code and upstream contracts; it does not establish successful notifications, capture, playback, or portal forwarding.

  • D-Bus: authenticate to the proxy, exercise an allowed service, and verify a disallowed service is blocked. Display a notification, update/close it, and receive an action callback. Confirm local systemd and snapd remain functional.
  • Camera: enumerate devices, capture visible frames in Firefox, deny website permission, then test hotplug and Workshop disconnect. Device listing alone is insufficient.
  • Audio: verify real sinks and non-monitor sources, hear playback, and record intelligible microphone audio. Test host denial and revocation, not just sample byte counts.
  • Opening: exercise a web URL, mail handler, relative/shared file, and local file URI. Reject non-shared paths and symlink escapes. Test toolkit and Snap/portal callers separately.
  • Video: play a browser video with sound. Independently validate screen sharing, hardware decode, and DRM if they are in scope.
  • Lifecycle: stop/restart the bridge, refresh/reboot the guest, and reconnect after host reboot. Confirm cleanup, recovery, and actionable errors across both host and guest.
# Repeatable development checks:
workshop run dev -- test

# Guest audio service log:
workshop exec firefox -- journalctl --user -u workshop-pipewire-pulse --no-pager -n 80

Go tests cover protocol rejection, path/symlink escapes, peer checks, argument preservation, launch failures, locks, child shutdown, mount sequencing, and socket-inode preservation where binding is permitted. The Go suite also tests host/guest command dispatch, help without host initialization, invalid-command exit codes, the guest client protocol and CLI, and all three guest wrappers (audio, Firefox, and xdg-open). Wrapper checks cover local-bus isolation, Firefox’s delayed bus switch and missing-socket failure, argument preservation, and exit-status propagation. Logging tests cover split lines, trailing output, and child output routed through the command logger. The client and server use an in-memory connection for protocol tests. Browser capture/playback, notification actions, and Snap portal opening remain live acceptance checks.

Earlier implementation verification: the Go test suite passed with Go 1.26.7 and a temporary module file. The static binary built successfully, help/version smoke checks passed, and the guest hook and wrapper passed shell syntax checks. These earlier checks do not verify the committed Go 1.27 requirement or live desktop behavior.

Documentation review, 15 October 2026: All Go test packages passed in a fresh run with the local Go 1.26.7 toolchain and a temporary module file targeting Go 1.26. HTML structure, local documentation links/anchors, and all six SDK shell scripts’ syntax checks also passed. Workshop still failed at snap-confine; Go 1.27 and live desktop validation remain outstanding. The committed module and dev SDK require Go 1.27. Earlier race checks were blocked by an unavailable C compiler. Socket tests explicitly skip only when binding is denied by the sandbox.
